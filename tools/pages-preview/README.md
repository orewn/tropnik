# Статическая тестовая версия Тропника

Этот инструмент собирает текущий веб интерфейс для тестовой публикации в GitHub Pages. Он использует существующие страницы, компоненты, карту, рельеф и публичные данные. Исходные `web/app`, `web/components`, `web/lib`, `web/public` и `package.json` не изменяются.

## Сборка и локальная проверка

Запускать из корня полного проекта, где находятся `web` и `tools`. Нужен Node.js версии, указанной в `web/package.json`, Python 3 и уже установленные зависимости `web/node_modules`. Инструмент использует существующие Vite, TypeScript и React; не копирует зависимости и не выполняет установку пакетов.

```sh
node tools/pages-preview/fetch-apk.mjs
node tools/pages-preview/build.mjs --base /tropnik/ --origin https://orewn.github.io
node tools/pages-preview/serve.mjs --dir web/pages-preview/dist --port 4176
```

Пример адреса локальной проверки: `http://127.0.0.1:4176/tropnik/`. Значения `--origin` и `--base` задаёт владелец публикации. Имя проекта не зашито в маршруты или сетевые обращения. Без аргумента `--origin` используется `http://localhost:4173`; без `--base` — `/tropnik/`. Поддерживается один непустой сегмент проекта, с начальным и конечным `/`.

`fetch-apk.mjs` выбирает APK по `architecture` в `web/public/downloads/android-manifest.json`: `arm64-v8a` соответствует `tropnik-arm64-preview.apk`, `universal` соответствует `tropnik-preview.apk`. Имеющийся файл принимается только при совпадении размера и SHA256. Если файла нет, инструмент получает закреплённую версию из публичного GitHub Release `orewn/tropnik`, с ограничением размера до 100 МиБ, времени и редиректов. APK публикуется в локальном каталоге только после полной проверки. Подменённый существующий файл не перезаписывается. Команда `node tools/pages-preview/fetch-apk.mjs --check-only` проверяет только локальный файл, без сети. Обычная сборка тоже не скачивает данные и останавливается, если обязательный APK отсутствует. Проверенный APK остаётся входом сборки, но ни один файл `.apk` не попадает в staged-копию и статический архив Pages. Кнопка в staged-копии ведёт на точный versioned GitHub Release `orewn/tropnik`; исходная страница Site не меняется.

Манифест закрепляет сертификат тестовой подписи, исходный commit и номер Actions run. Для `universal` обязательны ровно три ABI (`arm64-v8a`, `armeabi-v7a`, `x86_64`) и сведения об исполнении того же APK: `testedArtifact`, `testedArchitecture`, совпадающий `testedUniversalSha256`, подтверждения проверки установленного файла и тестов. Текущий допуск относится к эмулятору x86_64; `physicalDeviceVerified` и `arm64DeviceExecutionVerified` остаются `false`. Эти поля переносятся из проверенных отчётов конкретной сборки после успешного Android workflow и проверки опубликованных байтов. До получения таких доказательств прежний манифест сохраняет прежнюю загрузку. Само скачивание по SHA256 не проверяет подпись средствами Android SDK и не заменяет этот выпускной допуск.

Автоматическая публикация из исходников, закреплённые Actions, первая загрузка release assets и проверка публичного адреса описаны в [pages-publication.md](../../docs/pages-publication.md).

Результат: `web/pages-preview/dist` и соседний ZIP с именем сегмента проекта. В каталог публикации нужно передавать содержимое `dist`, включая `.nojekyll` и `404.html`. В нём нет исходного серверного приложения. `dist`, `.stage` и ZIP исключены локальным `.gitignore`; инструменты и адаптер остаются исходниками проекта. Публикацию в GitHub этот инструмент не выполняет.

Для повторной проверки готовой сборки:

```sh
node tools/pages-preview/verify.mjs web/pages-preview/dist
node tools/pages-preview/verify-http.mjs web/pages-preview/dist
node web/node_modules/typescript/bin/tsc -p web/pages-preview/tsconfig.json
```

Полный браузерный проход `node tools/pages-preview/browser-smoke.mjs` по умолчанию выполняет все нативные действия, проверки производительности, ожидания неподвижной камеры и снимки без CDP Tracing. Для записи диагностических CPU/GPU-трасс первого выбора Алтая и перехода рельефа z4–5 запустите `TROPNIK_BROWSER_TRACE=1 node tools/pages-preview/browser-smoke.mjs`. Набор профилей, пороги допуска и схема итогового отчёта при этом не меняются. Другие непустые значения `TROPNIK_BROWSER_TRACE` отклоняются до запуска браузера. Отдельный режим `TROPNIK_BROWSER_DIAGNOSTIC=terrain-close` автоматически записывает трассу высокого масштаба; его отчёт остаётся диагностическим и не допускает публикацию.

Проверка другого префикса без изменения первой сборки:

```sh
node tools/pages-preview/build.mjs --base /rf-preview/ --origin https://preview.example --out /tmp/tropnik-pages-preview-rf/dist
```

## Что сохраняется

- CSS импортируется в порядке текущего `web/app/layout.tsx`, включая `tropnik-system.css`, `map-design.css`, `place-stories.css` и локальные пакеты Manrope. Отдельная адаптация добавляет только обозначение тестовой версии.
- Список регионов и маршрутов вычисляется из текущего `content.ts` и всех его JSON импортов. Географические исключения из паспорта покрытия действуют и в статическом каталоге.
- Все страницы получают собственный `index.html`; известные адреса, конечный слеш и `index.html` разрешаются одним и тем же модулем маршрутизации, который используется в браузере и тестах.
- Относительные и пакетные импорты остаются относительными. Публичные адреса карты, её ограничений, стилей, шрифтов, спрайтов, worker, данных, загрузок и офлайн интерфейса получают префикс проекта. Сетевые политики загрузки карты преобразуются вместе с адресами.
- `offline-map` копируется побайтно. Каждый файл сверяется с размером и SHA-256 его манифеста. Паспорт `data/russia-boundaries-provenance.json` также остаётся побайтно исходным: его SHA закреплён в Android манифесте. Поле `assets.*.url` в этом исходном паспорте описывает исходный корень сайта; при ручном открытии нужно добавить префикс тестового проекта. Рабочие запросы интерфейса уже содержат этот префикс.
- APK выбирается по фактической ссылке исходной Android страницы и её манифесту. Проверяются обе локальные ветви, включая ещё не выбранную, и SHA256 в ключе кеша; затем только staged-ссылка заменяется на точный адрес `https://github.com/orewn/tropnik/releases/download/v<VERSION>/<SELECTED_APK>`. Подмена repo, tag, asset или query не допускается. Размер загрузки и описание совместимых процессоров продолжают зависеть от того же манифеста. `build-info.json` сохраняет `delivery: "github-release"`, размер, SHA256, сертификат и Android source/run отдельно от web source. Локальный выбранный APK обязателен: отсутствие, иной размер или SHA256 останавливают сборку без сетевой подкачки. Статическая проверка требует отсутствия любых `.apk`; это уменьшает архив на размер проверенного бинарника, но не гарантирует время Pages deployment. Физическое устройство, подпись для магазина и полевая навигация требуют отдельных проверок.

## Границы тестовой публикации

Это клиентская статическая сборка через Vite, а не сервер Next.js и не production SEO экспорт. Все HTML страницы, включая автономные, содержат `noindex`; `robots.txt` запрещает обход. Текущие SEO настройки основного приложения не изменяются.

API заменяется явной границей недоступности: состояние сервиса `false`, действия возвращают `503 static_preview`, сетевые запросы входа, регистрации, чатов и других серверных операций не выполняются. Статический адаптер не имитирует успешные ответы или пользователей. Серверные модули, API обработчики и backend запрещены в графе сборки. Локальные черновики и сохранение публичных данных в браузере остаются доступными; ключи хранилищ и Service Worker изолированы префиксом проекта.

Карта России и справочные маршруты имеют те же ограничения происхождения и проверки, что в исходном приложении. Тестовая публикация не повышает статус маршрутов до навигационных или открытых сейчас. Объёмный рельеф и подробный офлайн пакет ограничены пилотным районом Бзерпинского карниза.

## Воспроизводимость и проверки

`build-info.json` содержит конфигурацию, SHA-256 входных файлов, набор CSS, сведения о фактическом APK и граф включённых модулей. В Actions также записывается полный `GITHUB_SHA` исходного checkout; при локальной сборке поле `sourceCommit` остаётся `null`. `page-manifest.json` содержит точный список страниц. `verification.json` и `http-verification.json` сохраняют результаты проверок конкретной сборки. ZIP создаётся со стабильным порядком и фиксированной датой файлов.

Проверки выполняют реальный собранный router, политику ресурсов карты и адаптер API; проверяют исключённые географические маршруты, контрольные суммы покрытия и APK, отсутствие server modules, ссылки на публичные ресурсы, наличие terrain worker, noindex, область Service Worker и целостность всего офлайн пакета. Локальная HTTP проверка проверяет адрес проекта, прямые страницы, редиректы, 404, MIME и загрузку статических ресурсов под префиксом.

Эти проверки не заменяют просмотр браузером, установку APK на физическое устройство или проверку уже опубликованного GitHub Pages сайта. Они не объявляют доказанными FPS, WebGL2 на конкретном устройстве, доступность серверных функций или текущие условия маршрутов.

После успешного deploy workflow запускает `verify-deployed.mjs` без токена. Он сверяет ожидаемые build ID и commit, главную страницу и её JS/CSS, прямые страницы, автономный просмотрщик и территориальные данные строгими same-origin запросами без перенаправлений. APK проверяется отдельным анонимным запросом к точному GitHub Release с прежним allowlist редиректов, лимитом времени и полным размером/SHA256 потока; одного HEAD или query-параметра для допуска недостаточно. Запросы, требующие перенаправления на вход, не считаются успешными. Для ручного запуска нужны точные идентификаторы именно опубликованной сборки:

```sh
node tools/pages-preview/verify-deployed.mjs https://orewn.github.io/tropnik/ BUILD_ID SOURCE_COMMIT
node --test tools/pages-preview/tests/*.test.mjs
```

Отдельный `pages-preview/tsconfig.json` проверяет адаптер и импортируемые им страницы. Он наследует настройки проекта, но не включает генерируемые валидаторы Next: статической сборке не нужен работающий или актуальный `.next` каталог. Обычная проверка всего основного приложения остаётся отдельной задачей его собственного build процесса.
