Он продолжает [реально опубликованный промежуточный 0.4.31](release-0.4.31.md)

## Точечное изменение камеры

Pages-прогон 0.4.31 на `7d517c96` отказал на phone line witness: после
закрытия панели и двух реальных zoom-нажатий не нашлось видимой линии.
Предыдущий Pages `baf0b9ef` прошёл; эта разница не устраняет воспроизводимую
зависимость результата от последовательности событий.

Исправление согласует ожидающее перекадрирование с ручным zoom и
учитывает видимую область с отступами панели. Критерий приёмки — сохранение
выбранной области и настоящей линии в доступной части карты при этой
последовательности. Увеличение таймаута или пропуск проверки видимости не
являются исправлением. Исходные координаты маршрутов и маска сохраняются.

После изменения общих исходников повторно сгенерированы и проверены
web/Android runtime и манифесты. Точный локальный результат и границы
подтверждения записаны в [camera receipt](verification/camera-0.4.32-local.json).
Старые runtime hashes 0.4.31 не подставляются в receipt новой поставки.

## Запуск серверного контура

Изолированный [run 43398081327](https://github.com/orewn/tropnik/actions/runs/43398081327)
на source `a70424d969e61bdbda4e7dad7c7d86de3b154261` прошёл unit/race/vet,
проверку образа PostgreSQL/PostGIS, native integration и recovery. Он отказал
на отсутствии фактического loopback binding у API. Этот результат не является
успешной проверкой production-запуска.

Были найдены два отдельных дефекта. Проверка готовности ожидала плоский JSON,
хотя действующий API возвращает `data` и `meta`; проверка приведена к реальному
контракту. Кроме того, API и Next публиковали host-порты из исключительно
внутренней Docker-сети. Поддерживаемое разделение сетей описано в
[инструкции инфраструктуры](../infra/README.md).

В подготовленном варианте `backend` соединяет только БД, миграции и API;
внутренняя `application` соединяет API, веб и входной прокси; обычная
`frontend` доступна только прокси. Порты 8080/3000 привязаны к loopback
хоста на прокси. Внешняя сеть почты по-прежнему подключается явно и только
к API. Ключи и реальные учётные данные при этой работе не создавались.

Официальный Caddy закреплён по digest. Его parser проверил оба варианта
конфигурации, а независимая локальная проверка фактического транспорта
подтвердила сохранение метода, пути, тела, Origin, Host, cookies и доказательства
доверенного адреса клиента. [Transport receipt](verification/ingress-0.4.32-local-transport.json)
использует синтетические loopback upstream и не доказывает Docker-сети,
настоящие Go/Next процессы, SMTP или действующий сервер.
Точные hashes 14 замороженных файлов, версия Compose и результат parser
сохранены в [локальном отчёте ingress](verification/backend-0.4.32-local-ingress.json).
Независимый reviewer сверил все 14 файлов; шесть Compose/Caddy конфигураций
остались побайтно теми же, на которых выполнена проверка транспорта.

## Наблюдение за опубликованным обновлением

В публичном интерфейсе на Алтае уведомление «Доступна свежая версия» осталось
после двух явных нажатий «Обновить»; кнопка была доступна, приложение продолжало
работать. [Снимок наблюдения](verification/web-0.4.32-live-update-issue.jpg)
относится к существующей публикации, а не к новому кандидату.

Скрытое состояние registration/controller не извлекалось. Поэтому зависший
прогрев и замена waiting worker рассматриваются как проверяемые кодовые
сценарии, а не как доказанная причина этого конкретного живого случая.
Исправленный вариант ограничивает одну явно принятую попытку 15 секундами,
показывает «Обновляем…», затем предлагает «Повторить» при неудаче. Reload
допустим только после фактической смены контроллера относительно загруженного
документа. Таймаут и unmount снимают разрешение на позднюю перезагрузку;
переход waiting → active/activating → controllerchange и замена waiting worker
проверены отдельно. Обновление из другой вкладки оставляет выбор пользователю.

Фоновый прогрев ограничен общими 12 секундами: сетевые запросы отменяются,
`waitUntil` завершается даже при игнорировании AbortSignal транспортом,
продолжение работы не записывает пришедшие после отмены ответы. Проверка
SHA-256, 341 обзорного тайла через 57 уникальных загрузок и complete marker
сохранена. Сохранённые пользовательские карты не удаляются, unregister не
используется. Уже действующий старый worker может игнорировать новую команду
отмены; его ранее запущенная неограниченная задача не исправляется до активации
новой версии. Проверка обновления после публикации остаётся обязательной.
[Профильный отчёт](verification/web-0.4.32-local-update.json) сохраняет
41 проверку, RED→GREEN сценарии и границы доступных исходных логов.

## Security delta базы

Go **1.27.4** уже подтверждён [main gate 0.4.31](verification/backend-0.4.31-go-1.27.4.json).
Pillow **13.0.0** и границы проверки Go/Python описаны в
[dependency audit](verification/backend-build-dependencies-0.4.31.md).
Новый шаг — PostgreSQL **18.7**: оба прежних main drills фактически
использовали 18.6 / PostGIS 3.7.0.

Для полной защиты от изменений composite types недостаточно заменить
только PostgreSQL binary: C-extensions должны быть пересобраны с новыми
server headers. Подготавливаемый образ использует официальный пакет
PostGIS `3.7.0+dfsg-1.pgdg13+2`. Происхождение, checksums, фактические версии,
новые символы extension и строгий `composite_type_mismatch=error` проверяются
вместе с рабочими spatial SQL-операциями. Native concurrency, runtime grants,
схема 8, 32 таблицы, 16 guards и отрицательные recovery cases должны пройти
на окончательном образе. Dockerfile и отдельная проверка пакета этот gate
не заменяют.

0.4.31 с 0.4.25 не переносятся автоматически на 0.4.32. Постоянный production
signing key и испытание update-install остаются отдельными условиями.

## Сохраняющиеся границы

Полные исходные линии, отсутствие вымышленных соединений и совместимость
сохранённых данных обязательны. Счётчики раздельны: 621 уникальный источник /
22 456 частей / 404 749 вершин общего слоя и 624 файла по карточкам /
22 474 части / 405 833 вершины Android-пакета. Их повторная сверка относится
к фактическому payload новой сборки.

Live Go/PostGIS/BFF и SMTP, многоклиентский эксплуатационный сценарий,
физический ARM64, online-спутник на устройстве и production signing не
считаются выполненными по CI. Неограниченные семейства API, ESLint 9 EOL и
ограничение официальной Kotlin/AGP матрицы сохраняют ранее описанные границы.
Telegram-история, разрешённые Gotham/Quixel материалы и отсутствующие треки
по-прежнему требуют входных данных. Подробная автономная подложка всей России
не заявляется.
