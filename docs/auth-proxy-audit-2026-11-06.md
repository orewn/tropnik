# Проверка авторизации, прокси и SQL — 6 ноября 2026

**Исправлен подтверждённый дефект:** BFF не передавал проверенный адрес клиента,
поэтому посетители сайта делили один IP-лимит Go API. Дополнительно лимиты входа
хранились в памяти отдельного процесса и сбрасывались при его перезапуске.
Теперь доверенный адрес проходит проверку на обоих концах, а auth-счётчики
сохраняются в PostgreSQL. Живой Go/PostGIS по-прежнему не развёрнут; исправление
исходников не означает, что опубликованный сайт уже обслуживает аккаунты.

## Модель доверия

Для self-host HTTPS-входом служит Caddy. Он **заменяет** заголовки `X-Real-IP`
и `X-Tropa-Proxy-Token` своими данными. Next BFF принимает один корректный IP
только при совпадении серверного 256-битного токена, проверенного через
`timingSafeEqual`. Go требует одновременно совпадение токена и адрес прямого
сетевого соседа из `TRUSTED_PROXY_CIDRS`. В Go сравнение также constant-time.
Произвольный `X-Forwarded-For`, цепочка IP, повторный заголовок, неправильный
токен или неполная настройка не становятся доказательством адреса посетителя.

Если доказательства нет, учитывается адрес прямого соединения. Это закрытый
отказ от доверия заголовку, а не отключение лимита. За ненастроенным BFF бюджет
останется общим. Отдельные API-клиенты идут Caddy → Go; веб — Caddy → Next → Go.
Публичные GET-запросы SSR не расходуют auth-бюджет и не нуждаются в IP-доказательстве.
Необходимость полного ingress для managed Sites остаётся отдельной задачей:
описанная схема не появляется автоматически после установки `TROPA_API_URL`.

В ответ клиенту передаётся только ограниченный `Retry-After` (1–3600 секунд),
а внутренние IP/токен/Set-Cookie upstream не копируются. Пользовательский Bearer
в BFF по-прежнему строится только из проверенного HttpOnly session cookie.
Проверка Origin для записей, ограничение тела, таймаут и запрет редиректов
сохранены.

Исходники: [BFF helper](../web/lib/backend-forwarding.ts),
[BFF handler](../web/app/api/backend/[...path]/route.ts),
[Go trust boundary](../backend/internal/httpapi/security.go),
[пример Caddy](../infra/Caddyfile.example).

## Общий бюджет входа

Миграция [003](../backend/migrations/003_auth_rate_limits.sql) создаёт таблицу
`auth_rate_limits`. В ней нет plaintext email или IP: идентификатор —
HMAC-SHA256 со стабильным серверным ключом и отдельным пространством для каждой
категории. Email нормализуется так же, как для входа; IPv4-mapped IPv6 в Go
приводится к обычному IPv4, чтобы один адрес не получал два бюджета.

| Ограничение | Реализация |
|---|---|
| Регистрация + вход по IP | 20 попыток в 60-секундном окне |
| Вход по нормализованному аккаунту | 10 попыток в 60-секундном окне, включая неизвестные аккаунты |
| Совместное использование | Atomic PostgreSQL upsert; один ключ у всех экземпляров API |
| Отказ | Счётчик фиксируется, 429 возвращается с остатком окна; ошибка БД даёт 503 |
| Истечение | По времени БД; повторные отказы не продлевают окно |
| Очистка | Отдельный autocommit, не более 64 просроченных строк, `SKIP LOCKED` |
| Защита данных | Только scope, HMAC, счётчик и timestamps; не plaintext идентификаторы |

Счётчик и очистка выполняются разными autocommit-запросами: отказ не откатывает
попытку, а блокировка текущего ключа не удерживается во время очистки чужих
ключей. Счётчик ограничен сверху, чтобы повторные отказы не переполняли integer.
При простое старые строки могут оставаться до следующего трафика либо
плановой ограниченной очистки; истечение бюджета не зависит от физического
удаления строки. Это не обещание фонового TTL-worker.

Источник: [SQL операции](../backend/internal/store/auth_rate.go),
[HMAC идентификаторы](../backend/internal/auth/rate_identity.go),
[runtime grants](../backend/migrations/grants.go).

## Конфигурация и обновление

1. Применить миграцию 003 и обновить grants через owner/migration credential.
   `/api/v1/health/ready` теперь требует `migrations.RequiredVersion = 3`.
2. Установить независимый `TROPA_AUTH_RATE_KEY`: 64 hex-символа, одинаковые у всех
   экземпляров API. Не создавать новый ключ при каждом старте. Его ротация
   меняет пространство отпечатков и сбрасывает текущие бюджеты.
3. Для прокси установить **другой** `TROPA_PROXY_TOKEN` в Caddy, Next и Go, а также
   точные `TRUSTED_PROXY_CIDRS` в Go. API отклоняет неполную пару настроек и
   повторное использование auth-ключа. Не выдавать эти значения браузеру/APK.
4. Обновить все экземпляры API и проверить реальный путь двух разных клиентов.
   До завершения обновления старые процессы не разделяют новые бюджеты.

Приватные порты остаются закрытыми снаружи. Если компоненты находятся на разных
хостах, нужны HTTPS и проверка реальных ingress-соседей; доверие широкому
непроверенному диапазону не заменяет такую проверку. Полная инструкция находится
в [infra/README](../infra/README.md). В эту поставку не записаны реальные секреты.

## Ограничения проверки БД

Доступный executor имеет только UID/GID mapping `0 → 0`, размер 1, и
`setgroups=deny`. Штатное снижение привилегий через
`setpriv --reuid=65534 --regid=65534 --keep-groups` не удалось: `setresuid`
вернул `Invalid argument`. Docker/Podman/native PostgreSQL здесь недоступны.
Защита PostgreSQL от root не изменялась, дополнительные UID не создавались,
изоляция и ограничения не обходились.

Вместо ложного native PASS создан [воспроизводимый compatibility harness](../tools/db-compat/README.md).
Он использует официальный PGlite 0.5.15 / PostgreSQL 18.6 и экспериментальный
PostGIS 3.6.2, PGwire на локальном временном порту и один реальный SQL-сеанс.
У каждого теста новая схема; вызываются настоящие Go/pgx методы, миграции и
assertions. `SET ROLE` проверяет SQL-права, но **не** SCRAM, pg_hba, TLS или вход
ограниченной роли через отдельное сетевое соединение. Односессионная модель
не доказывает правильность одновременных транзакций.

Поэтому native gate с PostgreSQL/PostGIS, конкурентные join/post/auth сценарии,
контейнеры/Caddy, backup/restore, реальная регистрация и сквозной client/API/DB
запуск остаются обязательными перед production. Лимит общего числа mutation
запросов и четыре password-hash слота пока локальны процессу; сетевой DDoS,
контактная верификация, восстановление/удаление аккаунта и операционные процессы
модерации этой ограниченной правкой не заявлены завершёнными.

## Первичные источники

- [PostgreSQL initdb](https://www.postgresql.org/docs/current/app-initdb.html):
  штатное требование непривилегированного пользователя.
- [PGlite extensions](https://pglite.dev/extensions/) и
  [PGlite socket](https://pglite.dev/docs/pglite-socket): экспериментальный
  PostGIS и односессионная модель сокета.
- [Docker PostGIS](https://github.com/postgis/docker-postgis): свежий README
  от 2026-11-05 рекомендует **18-3.7 / PostGIS 3.7.0**. Более старый поисковый
  snapshot с 18-3.6 был перепроверен и не использован для downgrade.
  Прямой официальный tag API также вернул active 18-3.7. Образ локально не
  запускался; найденный digest не назван испытанным.
- [Cloudflare Node crypto](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/)
  и [Node net](https://developers.cloudflare.com/workers/runtime-apis/nodejs/net/):
  серверные built-in API, без добавления production-зависимости.
