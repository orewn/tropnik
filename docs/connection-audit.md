## Исправление недостоверного статуса

Ранее `/api/status` называл сервис подключённым по наличию `TROPA_API_URL`. В исправленном коде `connected:true` появляется только после ответа Go **HTTP 200**, корректного JSON `data.status:"ready"`, `meta.mode:"production"` и отсутствия `error`. Проба имеет предел три секунды, `no-store`, запрет редиректов, не отправляет пользовательские cookies/токен и читает не более 4096 байт. Ответ браузеру не содержит адрес backend, текст исключения или секреты.

| Условие | Ответ `/api/status` | Поведение существующего UI |
|---|---|---|
| URL отсутствует | HTTP 200, `configured:false`, `connected:false`, `mode:"preview"` | Формы регистрации/входа отключены, показан понятный preview |
| URL задан, readiness подтверждён | HTTP 200, `configured:true`, `connected:true`, `mode:"connected"` | Можно обратиться к настоящим авторизационным API |
| URL некорректен, сервер/БД недоступны, JSON неверен или истёк таймаут | HTTP 503, `configured:true`, `connected:false`, `mode:"unavailable"` | Ошибка с повторной проверкой; не ложный зелёный статус и не подмена отказа preview-режимом |

Проверка в момент времени не гарантирует последующий успех записи. Каждый API-запрос по-прежнему проверяет авторизацию, состояние и версию. Готовая БД также может законно не содержать опубликованных маршрутов или групп. Исправление статуса не создаёт недостающий сервер.

В нативном клиенте readiness подключён к реально используемой цепочке обновления: `OnlineViewModel.refreshData` → `ApiClient.checkHealth` → `/health/ready` → `DB.Ready`. Эта связь скомпилирована и проверена по исходникам; транспортные случаи выполнены на TLS MockWebServer. Время загрузки карточек и наличие сохранённого адреса не считаются готовностью. Карта и сохранённые данные не блокируются при неудачной проверке. Фактическая проверка новой Android-сборки и её хеши фиксируются в [BUILD-VERIFICATION](../android/BUILD-VERIFICATION.md).

## Что блокирует живую социальную часть

1. В production Sites нет ни одной runtime-переменной; локальные `.env` не заменяют эту конфигурацию. `web/.openai/hosting.json` содержит `d1:null`, `r2:null`: архитектура использует внешний Go/PostGIS, а этот манифест его не создаёт.
2. В доступном executor не обнаружены Docker/Podman/PostgreSQL/psql/pg_ctl и Docker socket; `infra/.env`, `DATABASE_URL` и `PUBLIC_ORIGIN` отсутствуют. Загруженный Go toolchain позволяет собирать код, но не является запущенным сервером. Не предоставлены реквизиты существующего удалённого API/БД/хоста.
3. Миграции 001/002 и runtime grants ещё не проходили реальный PostgreSQL gate. Компиляция интеграционного теста не является его выполнением.
4. Для организованных выходов нужны реальные аккаунты оператора и гида, рассмотренная квалификация и опубликованная версия маршрута. В поставке намеренно нет подставных людей, разрешений и оценок.

Нативные Sites tools позволяют прочитать/задать runtime-переменные и переопубликовать сохранённую версию. Они не предоставили отдельного подключённого Go/PostGIS-хоста. В доступном наборе инструментов не обнаружен серверный/DB-коннектор для такого развёртывания. Нельзя сделать рабочую цепочку, просто записав придуманный URL.

Сравнение с параллельным проектом не добавило внешнего сервера: backend, миграции и infra сохраняются из текущего checkpoint, а полезные различия относятся к клиентам и рельефу. [Результат backend-сверки](merge-backend-review.md). Полная GitHub-публикация также не завершена: по последней проверке владельца публикации private `orewn/tropnik/main` содержит только README, есть лишь черновик релиза. Это отдельный вопрос доставки исходников, а не показатель доступности API.

## Минимальное реальное подключение

### Вариант: свой хост для всего приложения

Нужен доступ к действительному x86-64 Linux-хосту с Docker Compose, доменом и HTTPS. Скопировать `infra/.env.example` в `.env`, задать два независимых пароля и точный `PUBLIC_ORIGIN`. Затем выполнить процедуру из [infra README](../infra/README.md):

```bash
cd infra
docker compose -f compose.yaml -f compose.web.yaml --env-file .env up --build -d
curl --fail http://127.0.0.1:8080/api/v1/health/ready
```

Порядок: PostGIS healthy → миграции 001/002 и grants → API с ограниченной ролью → Next. Внутренний BFF уже получает `TROPA_API_URL=http://api:8080`. Caddy направляет `/api/v1/*` к Go, остальные запросы, включая `/api/backend/*`, к Next. Для внешнего PostgreSQL используется проверяемый TLS; исключение private-network применяется только к документированной изолированной Docker-сети.

### Вариант: сохранить текущий Sites-фронтенд

Развернуть Go API/PostGIS отдельно за настоящим HTTPS origin. Проверить `/api/v1/health/ready` снаружи. После этого через `sites_update_environment_variables` задать **`TROPA_API_URL` равным origin без `/api/v1`** и переопубликовать сохранённую версию, чтобы новая env revision применилась. Audience owner-private сохраняется. Строка БД остаётся на backend-хосте, не в браузере и не в `NEXT_PUBLIC_*`.

В Android указать origin этого же Go сервиса либо полный HTTPS URL с `/api/v1` в «Профиль → Подключить сервис». URL приватного Sites сам по себе не является Go API endpoint; gate входа ChatGPT не заменяет нативную сессию приложения.

Для реального публичного трафика настроить доверенный ingress, серверный `TROPA_PROXY_TOKEN` на Caddy/Next/Go и точные `TRUSTED_PROXY_CIDRS` на Go. Исправленный BFF передаёт IP только с корректным доказательством; Go дополнительно проверяет сетевого соседа. Без доказательства используется адрес прямого соединения, поэтому отсутствие настройки не разрешает подмену IP, но оставляет общий бюджет BFF. Отдельный стабильный `TROPA_AUTH_RATE_KEY` обязателен для HMAC-идентификаторов общих PostgreSQL-лимитов. Миграция 003 и runtime grants применяются до запуска нового API. [Инструкция self-host](../infra/README.md) описывает обе цепочки. Для managed Sites такая доверенная цепочка автоматически не появляется.

### APK для self-host

Полный source ZIP **не содержит APK**. На опубликованном Site файл добавлен отдельно. Перед собственной веб-сборкой положите переданный финальный ARM64 APK в `web/public/downloads/tropnik-arm64-preview.apk`. Если APK собран из исходников штатным скриптом, команда из корня проекта:

```bash
mkdir -p web/public/downloads
cp android/dist/tropnik-arm64-preview.apk web/public/downloads/tropnik-arm64-preview.apk
```

Если используется переданный отдельно APK, источник команды `cp` — путь к этому файлу. Сверить его SHA256 с финальным Android-отчётом. Затем собрать веб; Docker копирует `public/` на этапе build. Этот deployment-шаг уже указан в [README](../README.md).

После подключения выполнить реальный registration/group/chat/guide scenario и [PostGIS gate](acceptance.md). Никакой положительный unit-тест не отмечает этот ещё не выполненный live E2E как пройденный.
